# Vitis 裸机工程迁移到 PYNQ：接口与证据流程

## 目标、输入与边界

目标是建立可审查的迁移和验证流程，适用于 Zynq-7000 或其他受目标 PYNQ 镜像支持的平台，尤其是 AXI-Lite 控制、AXI Master 访存、DMA/VDMA、摄像头 I2C 组合。输入包括裸机源码/驱动、XSA、匹配的 bit/HWH、板卡原理图/约束、镜像版本、测试数据与黄金参考。

流程与应用类别解耦；寄存器地址、IP 名、尺寸、量化参数、权重布局和外设总线必须从目标工程提取。没有这些契约时停止相应硬件调用，不能试写未知寄存器。仅有 ELF/XSA 的恢复流程不能承诺可重新综合。Versal、Alveo、不同 DMA 控制器或不同内存架构须另核对其运行时接口。

## 1. 盘点和配对

1. 保留原包，记录 SHA-256；将源码、硬件交付件、模型、数据、报告分别盘点。读取活动源码，确认任务、类别顺序和实际参数，避免被旧文件名误导。
2. 记录 Vivado/Vitis 构建版本、器件完整型号、板卡版本与 I/O 电压。XSA 是 ZIP 归档，可离线列出内容并提取其中匹配的 bit/HWH；不要把另一个版本的 HWH 拼接到 bitstream。
3. PYNQ Overlay 文件使用同一基名，例如 `vision.bit` 与 `vision.hwh`，置于同目录。将原始 XSA 哈希、内部路径、提取文件哈希写入清单；同名不能证明同源。
4. 比较 HWH 中 IP 类型、地址、时钟和中断与裸机 `xparameters.h`、驱动头文件。板卡/器件/引脚电压与启动镜像不符时，先解决兼容性再下载。

依据：[PYNQ Overlay Design](https://pynq.readthedocs.io/en/latest/overlay_design_methodology/overlay_design.html)。

## 2. 建立接口契约

为每个 IP 形成表格：VLNV/驱动类型、实例名、基地址/地址范围、寄存器偏移、字段宽度、访问语义、指针地址位宽、数据类型、张量布局、步长、缓存方向、开始/完成位和超时时间。

优先利用解析出的 `ip_dict` 与可用的 `register_map` 交叉核对。HLS 的 `ap_done` 可能有读清行为；不要反复读取造成状态丢失。区分直接 AXI Master 指针接口和 AXI DMA 流接口：前者不能套用 `dma.transfer()`。地址写入须覆盖真实位宽，不能把 64 位地址静默截成 32 位；若 IP 仅能访问 32 位物理地址，应检查已分配缓冲是否在可寻址范围内。

## 3. Linux 内存与缓存

裸机常量如 `0x10000000` 不表示 Linux 为应用保留了该区间。使用 `pynq.allocate(shape=..., dtype=...)` 分配 PL 可访问的连续缓冲，将 `.device_address` 传给硬件，不使用 `id()`、普通 NumPy 指针或裸机旧常量。缓冲尺寸、对齐、布局和 dtype 必须匹配硬件契约。

PS 写完输入/权重后，在 PL 读取前调用 `flush()` 或 `sync_to_device()`；确认 PL 完成后，PS 读取输出前调用 `invalidate()` 或 `sync_from_device()`。普通 NumPy 可作为 CPU 参考，不能假定它是 DMA 缓冲。输入数据写入、缓存同步和计时边界需明确记录。

依据：[PYNQ Allocate](https://pynq.readthedocs.io/en/latest/pynq_libraries/allocate.html)。

## 4. 等待、异常与缓冲生命周期

使用单调时钟实现有界等待，超时时记录控制寄存器、错误位、传输长度、缓冲设备地址及哈希/环境标识。成功完成后再同步输出和检查参考结果。DMA 流核还需核对长度、TLAST、TKEEP、DRE/对齐和 IP 的最大传输配置。PYNQ 常规 DMA 驱动与 VDMA 不是可互换接口。

**超时后不能立即 `freebuffer()`、退出自动释放缓冲的上下文，或丢失缓冲最后一个引用。** Python 超时只说明主机没有观察到完成，PL 仍可能继续 DMA 访存。保留对缓冲和控制对象的引用，将设备标记为不可继续提交；通过明确支持的停止/复位顺序确认所有访问主机内存的 AXI Master 均已停止，再释放。单独停止某个通道或盲目重载 Overlay 不足以自动证明所有访存已停止。无法确认停止时，保持缓冲保留，结束本轮测试，按板卡恢复流程重启；不要在该进程继续复用这些地址。

这是基于异步设备访存生命周期的工程约束，尚未在本项目中实测故障恢复。对应驱动的 reset/stop 语义必须查目标 IP 文档后实现。

依据：[PYNQ DMA](https://pynq.readthedocs.io/en/latest/pynq_libraries/dma.html)。

## 5. 外设与设备树

先识别 I2C 控制器：PS I2C 的 Linux 驱动路径和 PL AXI IIC 的 PYNQ 驱动路径不同。通过板卡原理图、PS 初始化、HWH、设备树和 `/sys/class/i2c-dev/` 交叉确认。只加载 Overlay 不能保证 PS I2C 的 MIO/EMIO、时钟、引脚复用与 Linux 设备树节点已经启用。总线号可能变化，不能默认摄像头永远位于 `/dev/i2c-0`。

先执行只读的适配器枚举 `i2cdetect -l`，再按已确认设备协议读取芯片 ID。不要将扫描或初始化寄存器脚本当作只读枚举。核对 7 位地址与旧裸机的 8 位读/写地址表达方式；按设备协议实现 16 位寄存器地址和必要的组合事务。确认驱动占用、权限、复位、外部时钟和供电后才进行初始化。

依据：[Linux I2C userspace interface](https://www.kernel.org/doc/html/latest/i2c/dev-interface.html)、[PYNQ AXI IIC](https://pynq.readthedocs.io/en/latest/pynq_package/pynq.lib/pynq.lib.iic.html)。

## 6. 分阶段验证与验收

1. 离线：提取配对、元数据解析、寄存器/模型尺寸检查、预处理黄金参考、错误路径检查。明确写“离线通过”，不写“上板通过”。
2. 板上只读预检：板卡/镜像/PYNQ 版本、器件、空闲内存、外设适配器、Overlay 元数据与实际地址一致性。
3. 低风险小输入：先验证缓冲传输和单核输出，再组合摄像头/显示和完整模型；所有输出与同输入、同量化的黄金结果比对。
4. 稳定性：重复推理、异常输入、受控超时与恢复；确认没有缓冲泄漏或未停止访存。没有可控恢复机制时不开展破坏性故障注入。
5. 性能：预热后报告样本数、统计方法、核耗时和端到端耗时、基线、误差、资源与时序。保留原始日志；缺报告或缺硬件时保留空项。
6. 迁移复用：另一题目或另一板卡重新执行以上流程并保存配置差异和证据，之后才能声称相应范围内的通用性得到验证。

## 本次形成依据与当前验证状态

本工程提供 Vitis 2019.2 软件/驱动及多个 XSA，存在 1.8 V / 3.3 V 命名版本；活动类别是水稻病害六类，原模型参数加载指向外部权重路径。这些观察促使本流程强调同源配对、真实任务确认与权重完整性。缓存、DMA 缓冲生命周期和 I2C 检查来自裸机到 Linux 的接口差异及官方文档对照，并非已经观察到真实板上故障。

当前完成的是文件/文档审计和流程整理。尚未连接板卡，未验证推理精度、视频流、实测性能、超时恢复、第二板卡或第二题目；不得把本技能包视为这些结果的证明。
